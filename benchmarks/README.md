# Benchmarks

Keris is compared against Python using the same algorithms. Run from the project root:

```bash
python run_benchmarks.py
```

- **Scripts**: `bench_fibonacci.ks`, `bench_factorial.ks`, `bench_loop.ks` — runnable Keris programs.
- **Report**: `report.html` — comparison chart and times (generated by the runner).

Python is the baseline (1×). Keris is interpreted by Python, so it is expected to be slower.

## Why is Keris so much slower than Python?

The size of the gap (~100–170×) comes from *how* each language runs:

| | **Python** | **Keris** |
|---|------------|-----------|
| **Execution model** | Your code is compiled to **bytecode** once, then the CPython VM executes it (code in C). | A **tree-walk interpreter** in Python: no bytecode, just AST nodes. |
| **One operation** | One VM opcode (e.g. `BINARY_ADD`) ≈ one C-level step. | One “add” = Python calling `evaluate(binary)` → `evaluate(left)` → `evaluate(right)` → dict lookups, `isinstance` checks, etc. |
| **Loop of 200k iterations** | The same bytecode is run 200k times; the “add” is a single opcode each time. | The same AST is *re-traversed* 200k times: for each iteration we walk the tree for the condition and the body again. |

So for every Keris operation you get:

- Multiple Python function calls (`execute`, `evaluate`, `evaluate_binary`, …).
- Repeated `isinstance(expr, Binary)`-style dispatching.
- Variable lookups via `Environment.get()` (dict lookup, possible chain through enclosing scopes).
- No low-level “just add two integers” step; it’s all Python objects and method calls.

Python avoids that by compiling to a compact bytecode and running it in a tight C loop. Interpreters like Keris that walk the AST for every evaluation are flexible and simple, but pay a large speed cost. Making Keris faster would mean adding a bytecode compiler and VM (or compiling to another backend), not just tuning the current tree-walk loop.
