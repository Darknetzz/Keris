# Benchmarks

Keris is compared against Python using the same algorithms. Run from the project root:

```bash
python run_benchmarks.py
```

- **Scripts**: `bench_fibonacci.ks`, `bench_factorial.ks`, `bench_loop.ks` — runnable Keris programs.
- **Report**: `report.html` — comparison chart and times (generated by the runner).

**How Keris is run:** The benchmark uses **compile-to-Python** by default: Keris is transpiled to Python AST and executed with `exec()`, so it runs at **near–native Python speed**. Results are typically in the **0.9×–2.2×** range (Keris time / Python time), with Fibonacci often *faster* than Python due to different code shape.

Python is the baseline (1×). Lower ratio = Keris faster; higher = Keris slower.

## Typical results (compile-to-Python)

| Benchmark | Typical Keris / Python |
|-----------|------------------------|
| Fibonacci (recursive, fib(30)) | **~0.9×** (Keris faster) |
| Factorial (recursive, fact(100)) | ~1.0–1.1× |
| Loop (sum 0..199999) | ~2× (Keris slower) |

If you run with `--no-compile` (VM only) or `--tree-walk` (interpreter only), Keris is much slower; see below.

## Why was Keris so slow before? (tree-walk / VM only)

With **tree-walk** or **bytecode VM only** (no compile-to-Python), the gap was ~100–170× because:

| | **Python** | **Keris (tree-walk/VM)** |
|---|------------|---------------------------|
| **Execution** | Bytecode on CPython (C) | AST walk or bytecode VM in Python |
| **Per operation** | One opcode in C | Many Python calls, dict lookups, dispatch |

So every Keris operation cost many Python steps. **Compiling Keris to Python** removes that layer: the generated code *is* Python and runs on CPython directly.
